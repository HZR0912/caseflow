# ADR-0004：MockCorp 独立记录操作日志，且失败路径也写

- 状态：已接受
- 日期：2026-10-23（W2 收尾）
- 相关代码：`migrations/versions/0003_mockcorp_oplog.py`、`apps/mockcorp/store.py`、
  `apps/mockcorp/service.py`、`apps/mockcorp/main.py`

## 背景

CaseFlow 的核心卖点是"Agent 做的事可追溯"。但 W2 之前只有一条证据链：CaseFlow 自己的
`audit_log`。问题很直接——**自己写自己的审计，无法证明自己没撒谎**。Agent 可以声称
"我创建了 3 个账号、邀请了 2 个人"，而系统实际只收到 1 次调用；只要它自己的日志写得漂亮，
外部没有任何办法发现。

要形成可信的交叉验证，必须有一个**不归 Agent 管**的第二视角。MockCorp 作为"供给方"
天然适合承担这个角色：它只知道"我收到了什么请求、我给了什么结果"，不会被 Agent 的叙述
影响。

## 选项

1. **不记录，靠 Agent 自报**：成本最低，但"可追溯"只是口号，评测无法断言。
2. **只记录成功写入**：能核对"做了几件事"，但漏掉最重要的一类事实——Agent **尝试过**
   但被拒绝的操作。越权尝试、失败重试、预演，恰恰是评测最需要看的信号。
3. **记录所有进入事务的尝试，成功与失败同一张表**：多传一个 actor 参数、多一次 INSERT。

## 决定

选 3。`mockcorp_oplog` 记录每一次进入事务的写尝试，`outcome` 四态：

| outcome | 触发条件 |
|---|---|
| `committed` | 业务已落库（含幂等重放） |
| `dry_run` | 预演成功，业务未落库 |
| `rejected` | 业务规则拒绝或注入的瞬态故障 |
| `error` | 处理器抛出未预期异常 |

日志与业务的**提交语义不对称**，这是本次最重要的设计判断：

- 成功路径：业务状态、幂等收据、日志行在同一事务提交，不存在"改了数据没留痕"。
- 失败/预演/重放路径：业务变更回滚，日志行**单独提交**。理由是日志的职责是记录
  "这次尝试发生过"，尝试没落地不代表没发生。若为了"事务纯粹"把失败日志也回滚，
  这张表就失去了最关键的价值。
- 处理器抛异常：先补一条 `outcome=error` 的日志并提交，再把异常原样抛出。
  既留下现场，也不掩盖异常。

**边界（必须写清楚，否则会被误用）**：只有进入事务的请求才进日志。认证失败（401）、
请求体校验失败（422，Pydantic 在路由层就拒了）、缺少幂等键（400，在 `execute` 入口
直接返回）都不会出现在日志里。这些请求"没有到达业务"，由网关/访问日志负责，不在本表职责内。

`actor` 来自服务端凭据映射，不接受请求体自报——与 ADR-0002 同一条原则。

读取用 `GET /v1/oplog?after_id=&limit=`，按 `id` 升序，`id` 是 BIGSERIAL，天然单调递增，
可以直接当增量游标，适合评测跑完后拉全量做交叉核对。

## 代价

- **多一次 INSERT**：每个写请求多一次同事务插入，成本可忽略。
- **表会无限增长**：W2 不做保留策略或归档，模拟环境的量级不需要。真实系统要按时间分区
  或冷热分离，这是明确的未做项。
- **不对称的提交语义需要理解成本**：读代码的人容易误以为"日志和业务一定同生共死"，
  所以 `store.py` 顶部和本 ADR 都写明了原因。
- **不能替代 CaseFlow 的审计**：两者职责不同——MockCorp 记录"系统收到了什么"，
  CaseFlow 的 `audit_log` 记录"Agent 决定做什么、谁批准的"。交叉核对的价值正来自
  两个独立视角，而不是合并成一张表。

## 复核点

- 如果 W7 的执行器开始批量调用（一个请求触发 50 次工具调用），需要重新评估单表写入量，
  并考虑按租户分区。
- 如果评测发现"越权尝试"在日志里无法区分于普通拒绝，再给 `error_code` 加分类前缀，
  而不是新开一列。
