# ADR-0005：制度知识库——按条款切块、版本是块的属性、引用必须可验证

- 状态：已接受
- 日期：2026-10-23（W3）
- 相关代码：`core/rag/`、`migrations/versions/0004_policy_chunks.py`、`eval/run_rag_eval.py`

## 背景

W3 开始做产品的第一个"真正的功能"：让 Agent 能回答制度问题，并且答案可追溯到原文。
这不是从零设计 RAG，而是**针对企业制度这一种语料**做取舍。制度文本有三个特点决定了
它和通用文档问答不一样：

1. **回答错一条规定，代价是钱或权限**，所以"有出处"和"答对"一样重要；
2. **条款会被修订**，同一份办法存在多个生效版本，新旧规定在文本上高度相似；
3. **结构极规整**（章 / 条 / 款），结构本身就是最好的切分依据。

## 决定一：按条款切块，不按字数切

切到 `###`（条）。每块保留 `char_start / char_end`，指向源文件正文的字符区间。

被否掉的选项：

- **固定长度滑动窗口**：简单，但会把一条规定劈成两半。检索到半条比检索不到更糟——
  模型会照着半条补全，补出来的往往是错的。
- **整篇文档当一块**：40 个块变成 3 个，检索粒度太粗，命中后上下文里混着 14 条不相干规定。
- **按段落切**：制度里的段落常是列表项（城市分档、审批层级），单独成段没有意义。

代价：切块依赖文档遵守 markdown 标题规范。语料是我们自己整理的，这个前提成立；
如果要接入客户上传的 Word/PDF，必须先做版面解析，这不是 W3 的范围。

## 决定二：版本的属性放在块上，对齐键是「文档 + 条款标题」

`effective_date` / `superseded_date` 存在**块**上，不是文档上。检索时两版都参与排序，
排序后由 `resolve_versions()` 决定哪块是"当前有效"，其余进 `superseded` 字段。

这是本次最容易做错的一处，踩了两次：

**第一次错**：去重键用 `doc_key`。结果《差旅费用管理办法》的 14 条被压成 1 条——
问"实习生账号有效期"时，命中的条款被同文档的另一条挤掉，检索看起来正常、答案却是错的。

**第二次错**：去重键改成 `section_path`。2026 版在第五章插入了「第 10 条 出差期间加班」，
导致后面的「报销时限」从第 10 条变成第 11 条。用路径对齐时，两版被当成两条不同规定，
**同时留在结果里**，模型于是把"15 个工作日"和"30 个工作日"都念了一遍。

最终方案：`section_key` = 去掉「第 N 条」前缀后的标题文本。条款号会漂移，条款标题不会。

被否掉的替代方案：**只在提示词里告诉模型"优先用新版本"**。这等于把确定性判断交给
概率模型，而且没法测。评测集里的 4 个版本冲突用例正是用来锁住这一点的。

## 决定三：中文分词自己写，不用 jieba

`to_tsvector('simple', 中文)` 在 Postgres 里会把整段中文当成一个词元，检索必然失配。
所以中文切分放在应用层：拉丁词与数字整体保留，中文按字符二元组切。

不用 jieba 的理由：

- 制度检索靠的是**专有名词和数字**（「实习生」「90 天」「3000 元」），二元组足够精确；
- 二元组的失误方向是可预期的（会切出「生理」「产生」这类跨词碎片，产生少量噪声），
  而 jieba 对词典外新词的切分是**未知的**，更难排查；
- 少一个依赖。

代价：查询较长的自然语言问句时，噪声 token 会稀释相关性。这在 40 个块的规模下可以接受，
语料扩到几千块后应重新评估（复核点写在下面）。

## 决定四：引用必须由程序校验，不能只靠提示词

`core/rag/citations.py` 对每条引用做四件事：

1. chunk_id 必须真实存在；
2. quote 必须在原文里**逐字出现**（两侧用同一套 NFKC + 去空白归一化）；
3. quote 短于 8 个字符不算引用；
4. 校验通过后**重算** char_start / char_end，交给前端高亮，而不是信任模型报的位置。

这一条是直接从 MigraAgent 的失败里学来的：那套系统的引用编号是提示词要求模型自己写的，
从未被程序校验，结果出现过"资料里没有的地名 + 编造编号"的假引用。**带假出处的编造
比没有出处更危险。**

踩过一个 bug：最初只对 quote 调了 `normalize()`（含 NFKC 折叠，`，`→`,`），
原文侧只去空白，于是完全正确的引文被判成 `quote_not_found`。这个 bug 的方向是"误杀"，
危险在于它会让人误以为模型在编造，进而去改提示词，真正的问题（校验器）反而被掩盖。

## 决定五：离线评测默认只跑全文路

`OfflineIndex.search()` 默认 `with_vector=False`。这是实测调出来的：

| 口径 | recall@5 | MRR | top1 |
|---|---|---|---|
| offline-text（BM25） | 1.000 | **0.778** | **0.667** |
| offline-hybrid（+哈希向量） | 1.000 | 0.736 | 0.583 |

原因：特征哈希给**每个**候选一个 0.030~0.033 的分数，它那条"排名"接近随机，
而 RRF 只认排名。一个强信号（BM25 把正确条款排第 1）被噪声信号稀释成了第 2。

结论写进代码注释：**融合只有在两路都比随机好时才有增益。** 哈希向量不满足这个前提，
所以默认不参与；`--with-vector` 只用于验证融合管线本身能跑。真实 embedding 的融合
质量由 `--database-url` 口径单独报告，**两者不能混成一个数字**。

这个取舍也回答了一个常见质疑："你用哈希假装做了向量检索？"——不是，哈希只用于
测管线正确性，语义质量用线上口径测，报告里分开写。

## 代价与未做

- **语料只有 3 篇 / 40 块、12 个评测用例**。数字能说明管线没坏，不能说明系统好用。
  真实规模下 recall 会下降，届时需要重新标定。
- **没有 rerank**。`gte-rerank` 的接入留到 W5 编排时一起做——那时才有"检索→重排→生成"
  的完整链路可以测，现在单独接只是增加一个未经验证的组件。
- **没有 embedding 缓存与增量索引**。每次 ingest 全量重算，40 块无所谓。
- **评测集是我自己出的**，存在"自己给自己出题"的偏差。缓解：用例覆盖语义型/字面型/
  版本冲突型/数字型四类，且每个用例都写了它测什么。

## 复核点

- 语料超过 500 块时，重新评估分词（是否换 jieba）与是否引入 rerank。
- 接入真实 embedding 后，重跑 `--database-url` 口径，若 hybrid 不超过 text，
  说明这批语料的查询以字面匹配为主，应按延迟预算决定砍掉向量路——而不是默认全留。
- 接入客户真实文档时，必须先做版面解析与条款识别，否则 `char_start/char_end` 的
  "逐字校验"前提不成立。

## 复盘：一次外部审查查出的五个问题（2026-10-23 修复）

W3 交付后做了一次独立审查（由另一个模型读代码 + 连库实测），查出五个问题。
记录下来，因为**每一个都说明我当时的验证方式有结构性缺陷**，比 bug 本身更重要。

### 1. 线上全文检索路对自然语言问句 0 召回（最严重）

`_text_route` 用的是 `plainto_tsquery('simple', tokens)`，它把每个 token 用 `&` 拼成
AND 查询。中文二元组切分会产出「长多」「少天」这类碎片，只要有一个碎片不在条款里，
整条查询命中 0 行。实测 12 条评测查询**全部 0 命中**——所谓"混合检索"在线上
实际是纯向量单路。

**为什么没被发现**：`eval/run_rag_eval.py` 默认走的是 `OfflineIndex`（Python BM25），
根本没碰 SQL。离线绿了不等于线上绿了。
**修法**：改用 `to_tsquery` 的 OR 表达式（`a | b | c`），token 先转义掉 `& | ! ( ) :`
等操作符；新增集成测试断言"12 条评测查询的全文路都不为空"。
**教训**：**离线评测和线上路径必须是同一套断言**。只要两条路径的测试集不交叉，
其中一条坏掉就没人数得清。

### 2. 切块把下一章的标题吞进上一章末条

`stop = 下一个 ### 的位置` 忽略了 `##`（章）标题，于是每章最后一条把
`## 第 X 章` 一并吞进正文。同时"标题栈"因为 `cuts` 里只有三级标题而失效，
`section_path` 里从来没有章这一层。

**为什么没被发现**：测试断言的是 `doc.body[start:end] == chunk.text`——两边是同一段
错误的文本，自洽性检查永远成立。**自洽不等于正确。**
**修法**：终点改为"下一个任意级别标题"，路径改为"严格递减的祖先链"；
新增 `test_chunk_never_contains_another_heading` 这类**语义**断言。
（顺带发现：审查报告说"15/40 块受影响"，我实测修复前是 0 块——是我在审查前
已经改过一次切片起点，报告测的是更早的版本。结论仍成立，数字不成立。）

### 3. 版本解析没读 superseded_date

`superseded_date` 只存不查。如果查询词只命中已废止的旧版，它会作为**现行规定**返回。
另外两个缺陷：未来版本被塞进 `superseded`（以"历史版本"身份误导），
`top_k` 只截 `hits` 不截 `superseded`（top_k=1 时可能带回 12 条无关历史）。

**修法**：候选分三类——已废止进 superseded、未来版本直接丢弃、现行按条款取最新；
新增 `align_superseded()` 只保留与被返回条款同属一条的历史版本。

### 4. MockCorp 日志的 outcome 分类与单测替身不一致

`Outcome.outcome_of()` 只有三个返回值，处理器抛异常时落库的是 `rejected`，
而单测替身 `MemoryStore` 手写硬编码了 `"error"`——**替身比生产代码更正确**，
于是 bug 只在真库集成测试里暴露。同一个测试还有两个问题：先跑了一次 dry-run
却断言日志表只有一条记录；`MockCorp(PostgresStore(...))` 漏传 settings 直接 TypeError。

**修法**：生产代码补 `error` 分支；替身改为**调用生产的 `outcome_of()`** 而不是
自己写一套；测试断言改为两条（dry_run + error）。
**教训**：**替身里不允许出现业务判断**。替身只替存储，不替逻辑。

### 5. 制度语料与 MockCorp 的系统脱节

语料只有权限与差旅，MockCorp 的 Money（下单、绑席位、退款）没有对应制度；
反过来差旅报销没有工具可执行。到 W5 串 `retrieve → plan → dry_run` 时会两头对不上。
**修法**：新增《软件采购与席位管理办法》，覆盖金额分级、席位上限、绑定、退款、
余额不足；补 4 条对应评测用例。

### 这轮修复改变了什么

- 非集成测试从 136 增至 144，集成测试从 13 增至 15（含两条新增的全文路回归）。
- 检索评测从 12 用例增至 16 用例，MRR 0.778 → 0.833（语料变大，但也新增了采购类查询）。
- **最重要的一条**：`ingest(embed=False)` 过去的 `COALESCE` 写法根本没有清空向量，
  那个"验证全文路"的集成测试是假阳性。现在 SQL 显式写 NULL，并断言
  `embedding IS NULL` 的行数等于块数。
