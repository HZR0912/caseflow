# ADR-0009：审批绑定的加密参数与持久执行日志

状态：已接受。日期：2026-10-24。

## 背景

W6 的 checkpoint 只保存脱敏计划，不能在重启后还原创建账号所需的原始参数。
业务提交和本地 checkpoint 也不存在跨服务原子事务，超时可能发生在提交之后。

## 决定

W5 预演成功时通过服务端回调取得已验证的 Plan，将其认证加密后单独保存，并用
摘要绑定整个审批快照。密文绑定租户、审批 ID；接口不接受客户端补传执行参数。
新流程保留独立的审批 checkpoint 和执行 journal，通过同一个数据库会话锁串行推进。

每步调用前保存意图、稳定幂等键、累计尝试次数；成功只保存供应方资源 ID。
如果远端提交后本地尚未记录便崩溃，恢复发送原键，供应方返回原收据。
每次尝试重新授权，遇到未知提交结果明确保留 outcome_unknown。
重试预算和等待时间持久化；终态重放不调用供应方。业务失败立即停止，为 W8 提供
已完成步骤清单，但不执行补偿。

## 未采用的方案

- 把原文/vault 塞进 checkpoint：污染通用状态与审批响应的隐私边界。
- 执行时重新调用模型或重新从文本规划：审批对象与实际执行可能不一致。
- 由客户端补传占位符映射：无法证明补传内容就是已批准内容。
- 只依赖 checkpoint 去重：无法覆盖远端提交与本地保存之间的崩溃窗口。
- 重试生成新 key 或重置预算：分别造成重复副作用或无界重试。

## 代价与复核点

需要稳定密钥、备份与后续轮换方案；丢失密钥就无法执行旧审批。
当前 Fernet 单密钥用于开发阶段，生产化前复核 KMS、多密钥轮换、权限与保留期限。
旧审批没有原始参数，必须重新提交。MockCorp 自身业务库仍保存其业务所需的数据。

每审批持有一个连接锁，执行顺序串行；长 Retry-After 返回待恢复状态而非后台调度。
规模扩大时评估持久任务队列、租约与 fencing，但仍需供应方幂等契约。
最后一次尝试提交后丢失结果需要人工对账；W8 设计 Saga 时必须先解决未知结果，
不能在未确认提交状态时盲目补偿或创建新申请重做。
