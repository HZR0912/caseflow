# ADR-0014：按服务生命周期复用有界数据库连接

状态：已接受。日期：2026-10-25。

## 问题与证据

W11 串行通过不能覆盖并发数据库连接故障。本轮并发 4 再现 599/600；
直连并发 8 为 597/600，连接诊断捕获 Windows `Address already in use (10048)`，
无 PostgreSQL SQLSTATE。一轮完整直连回归发起 4,992 次同步、570 次异步连接。
这是客户端建连阶段的地址分配冲突证据，不能据此声称 PostgreSQL 连接数已满，
也没有证明整个 Windows 动态端口范围耗尽。

## 决定

- API 审批、执行和记忆共用一个异步 psycopg 池；MockCorp 共用一个同步池。
  `core/db/pools.py` 统一配置：各最多 8 条连接、最多 32 个排队请求、借用等待 5 秒，
  最小连接数为 0，连接建立超时仍为 5 秒。池在 lifespan 中打开和关闭。
- 评测整轮复用同样的池，不逐例建池；每例仍有独立租户、凭据上下文、业务状态。
  提交后恢复用例继续创建独立服务和新连接，保留“从数据库恢复”的验证语义。
  短生命周期脚本可用显式直连；长驻调用者必须传入共享池。
- 检查借出的连接是否可用；坏连接丢弃。连接维护可以重建物理连接，
  不重放已经执行的 SQL 或业务请求，不修改业务重试预算、授权超时和门禁。
- 供应方事务边界不变：业务状态、幂等收据和成功日志原子提交；
  失败/预演的业务回滚，尝试日志独立提交。
- PostgreSQL advisory lock 属于物理会话。审批会话退出时显式解锁，
  覆盖成功、拒绝、异常、取消；若清理失败则关闭连接，不能将持锁连接放回池。
- 池等待超时或排队满均转为原有存储不可用错误（HTTP 503），不继续业务写入。
  正常冲突仍是 `approval_busy_retry`，不能改成允许并发执行。
- 评测保存池统计、物理建连诊断和关闭状态。默认及 CI 使用并发 4；
  并发 8 是额外验证条件，不作为生产容量承诺。

## 代价与未采用方案

池会保留空闲连接并引入生命周期管理；多进程部署时每个进程有独立池，
数据库预算要按进程数计算，还要预留迁移、观测等连接。这里的 8 不是全系统总上限。

不继续用串行作为故障修复；不增加业务重试来遮盖建连失败；不修改 Windows
动态端口范围或 PostgreSQL `max_connections` 来绕过应用的高频建连。
暂不引入 PgBouncer，避免增加部署组件和会话锁兼容性问题。

## 复核点

真实数据库测试覆盖物理连接复用、同租户事务、互斥锁、取消与故障清理、
池满拒绝和应用退出。重复运行相同 600 用例的并发 4/8 回归，要求无失败、
无重复副作用、无授权降级，并检查实际连接数和池归还情况。

增加 worker、启用更多观测写入或接入新数据库消费者时，重新核算连接预算和等待时间；
持续压力与数据库故障矩阵仍属于后续工作。结果见 [验证报告](../database-concurrency-verification.md)。
