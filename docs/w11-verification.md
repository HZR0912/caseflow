## 从失败到修复

- 初次预检查发现运行中的 OPA 策略与仓库不同，拒绝执行；重载 OPA 后继续。
- 引用文件名 `access-control@2026.1.md` 被误当邮箱脱敏，来源无法回查。
  修复为仅保留已加载受控语料的精确文件名；真实邮箱仍脱敏，已有回归测试。
- 制度中的“绕过审批……按奖惩制度处理”触发注入检测，导致整次检索被放弃。
  现在排除被拦片段，逐字验证其余引用；全部片段被拦仍然拒绝，没有关闭检测器。
- 四个审批服务首次启动时，阻塞式 advisory lock 查询与 checkpoint 的
  `CREATE INDEX CONCURRENTLY` 形成死锁，数据库返回 `40P01`。
  改为有界的非阻塞抢锁等待，避免等待者长时间占用查询快照。
- 测试数据也有错误：入职描述与授权意图混淆；单人全部撤销误写成部分成功；
  席位上限引用断言没有使用原文“不超过 3 个”。修正输入与预期，不放宽引用/状态门禁。

初期诊断记录保留在 `eval/results/diagnostic*.json`。
[第一次完整失败报告](../eval/results/w11-bootstrap.json) 为 594/600：
五次引用断言失败和一次 OPA 降级。引用率 85/90、OPA 健康和全例通过三项门禁拒绝，
进程退出码为 1；该结果没有被安装为基线。环境超时没有重算成业务成功。

[第二次候选报告](../eval/results/w11-baseline-candidate.json) 为 599/600，引用已全部通过，
但一次 OPA 降级仍令门禁失败。随后把 harness 中每例创建客户端的方式改为整轮复用
HTTP 连接池，与实际 API 生命周期一致，并记录降级原因；不缓存授权，不增加超时，
不重试掩盖失败。早期报告不足以确定该网络异常的底层原因，连接复用后的结果另行验证。

连接复用后的基线候选 600/600 通过，随后
[并发 4 的独立回归](../eval/results/w11-concurrency4-failed.json) 为 596/600：
4 次数据库连接异常，OPA 无降级；全例通过门禁拒绝，退出码 1。
当时观察到本机到 5432 端口有 5532 条 TIME_WAIT 连接，但这不足以证明异常根因。
没有把数据库错误改判为通过，也没有增加数据库重试；功能回归默认改为串行，
并发参数仍可显式启用。最终串行结果只证明该运行条件下的回归质量，
不能用来声称并发 4 的连接问题已经解决。基线与最终运行的并发不同，P95 不作速度对比。

## 使用与边界

CI 已增加正式回归命令和失败产物上传。本轮没有提交代码、执行远程 GitHub CI，
也没有设置仓库分支保护；不能据此声称线上发布已被强制阻止。

这是已知内部回归集。业务包含同一流程的人数/权限/付费参数组合；对抗集由已知
W4 数据适配而来。规则解释器的五次重跑，不等于大模型随机采样的五次稳定性。
未使用真实模型 API，没有 LLM judge 或人工校准分数；token/模型费用均为真实的 0。

Harness 使用真实数据库、HTTP OPA、本地供应方适配器。harness 中 restart 是
“远端提交后重建服务对象与连接”，不等于进程强杀。独立 W7 HTTP 演示验证了实际
强杀恢复，其原始记录为 `tmp/w7-check.json`，演示进程和数据库已清理。

引用检查证明原文、偏移、出处和主题符合要求；诱导编造场景只返回证据，不证明
自由生成答案的正确性。报告文件不是签名存证；代码、基线与场景仍需代码审查。
运行说明、判分口径及基线更新流程见 [W11 评测说明](w11-evaluation.md)。

## 这周存在的意义，用白话说

以前，我们能演示一次“办成了”。但改完代码以后，有没有把别处改坏，往往要靠人再点一遍。

这周把“检查有没有办对”做成了能重复运行的程序。它会故意给错误权限、漏掉审批、
制造超时、在提交后中断，再查数据库：有没有多建账号、多扣钱、该撤销的没撤销、
引用是不是瞎编的。以后有人改代码，这些检查会自动再跑，出问题就报失败。

这周已经实际找出引用损坏和审批并发死锁。它的价值在于减少“演示没问题，
换个条件就出事”的机会，也减少以后每次改动都靠人肉检查的成本。
它还不能证明 Agent 足够聪明；它让我们更有把握知道，已经做好的办事流程有没有被改坏。
